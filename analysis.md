# Network Orchestrator — анализ идеи и вывод

## Что это на самом деле

Идея эволюционировала от «универсального VPN-клиента» до **кроссплатформенного Network Orchestrator** — слоя, который:
1. Унифицирует модели интерфейсов/маршрутов/DNS поверх WG + OpenVPN + Xray;
2. Управляет несколькими туннелями одновременно с policy-based routing;
3. Визуализирует всю сетевую конфигурацию ОС и показывает эффективный путь до адреса.

## Что в идее действительно сильно

**Network Explorer (инвентаризация + визуализация) — самая ценная часть.** Она:
- решает реальную боль: Windows показывает адаптеры, маршруты и DNS в трёх разных местах, и человеку приходится собирать картину в голове;
- **работает без управления VPN** — то есть полезна даже тем, кому вообще не нужен VPN-клиент;
- технически низкорисковая: все нужные API на Windows (IP Helper, `Get-NetRoute`), Linux (netlink), macOS (SystemConfiguration) уже есть;
- кроссплатформенная по своей природе, потому что модель `NetworkInterface` одинакова везде.

Это та часть, которую стоит делать первой и которая может стать самостоятельным продуктом.

## Риски, которые недооценены в исходном обсуждении

**1. Scope.** Кроссплатформа × 3 VPN-протокола × routing engine × DNS × UI — это не MVP, это мульти-годовой проект. Даже «оркестратор существующих реализаций» означает координацию трёх независимых демонов, каждый из которых манипулирует маршрутами по-своему. Конфликты маршрутов между ними — отдельный класс багов, которые трудно дебажить.

**2. Windows — реально тяжёлая часть.** Нет policy routing как в Linux (`ip rule`), нет network namespaces, для domain/process routing нужен WFP, для своего TUN — Wintun + права админа. VPN chaining (WG→VPS→Xray) на Windows без глубокой драйверной работы может вообще не заработать чисто.

**3. Существующие альтернативы ближе, чем кажется.** sing-box / Mihomo уже умеют TUN + routing rules + multiple outbounds + domain routing. Главный пробел — «корпоративный WG/OpenVPN + proxy в одном UI». Вопрос: достаточно ли этого пробела, чтобы оправдать целый новый проект, или это скорее фича, которую sing-box мог бы добавить?

**4. Ниша узкая.** Обычный пользователь хочет «включить VPN». Админ настраивает маршруты сам. Целевая аудитория — power users с 5+ VPN, homelab, DevOps. Это реальная аудитория, но маленькая. Для open-source проекта это нормально; для продукта — вопрос.

**5. Maintenance burden.** 3 OS-адаптера × 3 протокола = 9 поверхностей интеграции, каждая ломается по-своему при обновлениях ОС или протоколов.

## Решение по скоупу (после обсуждения с автором)

Из проекта выкинуты самые тяжёлые и наименее необходимые части:
- **VPN chaining** — не нужен;
- **Кроссплатформа** — отложена, Windows-only на старте, macOS/Linux открыты для PR;
- **Process routing** — не нужен, только маршруты;
- **Domain routing** — реализуется через Xray routing engine (генерация config), а не собственный DNS-перехват.

## Пересмотренный scope

| Компонент | Сложность | Заметка |
|-----------|-----------|---------|
| Network Explorer (read-only) | ⭐⭐ | IP Helper API, чистый read |
| WireGuard backend | ⭐ | wireguard-go / существующий tunnel service |
| OpenVPN backend | ⭐⭐ | openvpn3 или обёртка над демоном |
| Xray/VLESS backend | ⭐⭐ | Xray-core embedded, TUN mode |
| IP-based split routing | ⭐⭐⭐ | маршруты ОС + метрики, без WFP |
| Профили + политики | ⭐⭐ | конфиг + state, чистый Core |
| Domain routing | через Xray | генерация Xray routing config, не своя реализация |

## Финальная архитектура MVP

```
                    GUI (Tauri + React)
                           |
                    Network Core (Rust)
                           |
            +--------------+--------------+
            |              |              |
      Network Explorer   Profiles      Policy Engine
      (read-only)        (state)        (IP/CIDR rules)
            |                             |
            +----------+-------------------+
                       |
                Platform Adapter (Windows)
                       |
            +----------+----------+----------+
            |          |          |         |
         WG        OpenVPN     Xray      IP Helper
         backend   backend    backend    (routes/DNS)
```

**Что Core делает сам:**
- модель `NetworkInterface`, `Route`, `Profile`, `Policy`;
- генерация Xray routing config из правил;
- применение IP/CIDR маршрутов через Windows routing API;
- сборка состояния интерфейсов для Explorer.

**Что Core НЕ делает:**
- не реализует VPN-протоколы (делегирует WG/OpenVPN/Xray);
- не перехватывает DNS (делегирует Xray routing engine);
- не трогает WFP / драйверы;
- не работает на macOS/Linux (открыто для PR).

## Порядок реализации

1. **Network Explorer** — read-only, интерфейсы/маршруты/DNS, «куда пойдёт IP». Польза сразу, без VPN.
2. **WireGuard backend** — самый простой (⭐), валидирует модель backend'а.
3. **Profiles + IP/CIDR policy routing** — применяет маршруты через Windows API.
4. **OpenVPN backend** — второй протокол, проверяет что модель масштабируется.
5. **Xray backend + domain routing через config** — закрывает bypass-сценарий.

Каждый этап самостоятелен и полезен. Если остановиться после 3 — уже рабочий WG-менеджер с split routing, чего нет ни в одном стандартном клиенте под Windows.

## Стек

**Rust + Tauri + React/TypeScript.** Не потому что Go плох, а потому что проект с большой вероятностью упрётся в TUN/packet-level/системные API, и Rust сэкономит на переписывании через год.

## Вывод

**Стоит реализации.** С текущим скоупом это:
- реалистичный MVP для одного разработчика (Network Explorer — недели, не месяцы);
- решает реальную боль автора (5 VPN, маршруты, контроль);
- имеет аудиторию (power users, DevOps, homelab);
- не упирается в самые тяжёлые технические проблемы (WFP, chaining, process routing, кроссплатформа);
- Network Explorer полезен как самостоятельный продукт, даже если VPN-часть не взлетит.
