# CLI `netorch`: один бинарник вместо россыпи конфигов (2026-10-15)

**Статус:** реализовано для macOS (2026-10-15): `crates/engine` (типизированный
`Engine`, трейт `Privileged`), `crates/cli` (`netorch`), режим `sudo` с
исполнителями хелпера в процессе, допуск `netorch` в политике пиров хелпера,
упаковка в бандл. Отличия от первоначального наброска:

- Библиотека профилей (импорт, подписки, правила маршрутов) пока вызывается
  через `net_manager_macos_bridge::call` — те же сервисы, что у нативного
  клиента; перенос в `engine` — отдельный шаг.
- Проверка подписи кода (`SecRequirement`) не сделана: политика пиров
  по-прежнему путь исполняемого файла (приложение и `netorch` из своего
  бандла).
- `sudo netorch service install|remove` сделан по выбору владельца: хелпер
  копируется в `/Library/PrivilegedHelperTools/com.netmanager.app.helper.cli`
  (root:wheel), launchd-метка `com.netmanager.app.helper.cli`, плист в
  `/Library/LaunchDaemons`; аргументы `--client` (приложение и `netorch`) и
  `--bundle .../Contents` (откуда брать закреплённый OpenVPN). Отказ, если
  хелпер уже отвечает на сокете (установлен приложением). Если позже
  поставить хелпер из приложения, сначала `sudo netorch service remove`:
  `bind_socket` перехватывает сокет у предыдущего владельца.
- Под root `netorch` ничего не пишет в каталог данных пользователя и не
  запускает бинарники из пользовательских каталогов; локальный Xray и правка
  профилей — только без `sudo`.
- Foreground-режим: `netorch up` держит процесс; `status`/`down` находят его по
  state-файлу (`runtime/netorch-up/` или `/var/run/network-orchestrator/netorch/`
  для запусков под `sudo`). `--detach` не сделан.

## Цель

`netorch up vless://…` (или URL подписки, `.conf`, `.ovpn`, имя сохранённого
профиля) должен сам: импортировать, выбрать порты и режим, сгенерировать
конфиг бэкенда, поставить маршруты и DNS, при ошибке откатить. Никаких
обязательных файлов настроек. Профили и данные общие с GUI.

## Почему bridge непривилегированный (и почему CLI это не касается)

`crates/macos-bridge` — staticlib внутри процесса SwiftUI-клиента, то есть
процесс обычного пользователя. Root-операции (utun, маршруты, DNS) из него
возможны только через повышение: root-приложение целиком (UI от root),
пароль на каждое действие (`osascript`/`sudo`; нет постоянного состояния,
нет очистки после падения), setuid (небезопасно) или launchd-демон
(`SMAppService`). Для GUI выбран последний, плюс он переживает выход и
падение приложения и чистит за ним по журналу.

CLI — отдельный процесс, и у него есть путь без хелпера: **`sudo netorch up`**.
Это обычная модель для CLI (`wg-quick`, `openvpn`). `crates/macos-helper` —
библиотека (`XrayExecutor`, `WireGuardExecutor`, `OpenVpnExecutor`, `Journal`,
`RealPlatform`), её исполнители запускаются внутри процесса CLI напрямую,
без сокета и без установки хелпера.

Правило `AGENTS.md` «bridge не получает мутаций» остаётся в силе: `netorch`
— отдельный крейт, а не расширение bridge. В `AGENTS.md` добавить абзац про
него.

### Режимы привилегий `netorch` на macOS

Образец — NetBird/Tailscale: служба с root ставится один раз, CLI — обычный
непривилегированный клиент службы. Поэтому основной режим — хелпер.

1. **Основной: без root, хелпер установлен** — CLI говорит с хелпером по
   сокету, как GUI; `netorch up` не требует `sudo`, туннель переживает
   терминал. Нужно: (а) `AppClientPolicy` допускает `netorch` из бандла —
   вместе с проверкой подписи кода (`SecRequirement`), одной проверки пути
   недостаточно; (б) `sudo netorch service install|remove` регистрирует
   launchd-демон без GUI. Регистрация одна на систему (общий label с
   `SMAppService`): GUI и CLI видят друг друга и не конфликтуют.
2. **Запасной: root (`sudo netorch …`)** — исполнители хелпера работают в
   процессе CLI, хелпер не нужен. Журнал владения тот же, при старте
   `recover()`. Туннель живёт, пока жив процесс.
3. **Без root и без хелпера** — только пользовательские режимы (Xray
   SOCKS/HTTP, системный прокси). Для остального CLI пишет, как поставить
   службу или запустить через `sudo`.

Что сохраняем при запуске от root (инварианты из `AGENTS.md`):
- Xray TUN: Xray запускается от консольного пользователя (`SUDO_UID`,
  `SUDO_GID`; группы, gid и uid сбрасываются необратимо), только из
  hash-verified managed-установки. Не от root.
- OpenVPN: только закреплённая копия (SHA-256 зашит в код), без script
  hooks, конфиг через `sanitize_openvpn_config`. Вне `.app` берётся
  бинарник из стандартного места установки `netorch` (см. открытые вопросы).
- WireGuard: userspace-движок в процессе, внешнего бинарника нет.
- Тесты на фейковых платформах, без реального utun/маршрутов/DNS.

### Конкуренция с GUI-хелпером

Два владельца одной сети недопустимы. Исполнители уже ведут журнал: перед
запуском CLI-режим 1 проверяет, что хелпер не держит туннель (`owned.list`
через сокет, если он доступен) или блокирует по `flock` на файле журнала.
Одновременно GUI и CLI могут управлять разными вторичными туннелями только
если это явно разрешено (по умолчанию — один первичный).

## Этап 0 (только macOS): вынести оркестрацию в `crates/engine`

Сейчас порядок «проверки → порты → запуск → ожидание → маршруты → откат»
живёт в `crates/macos-bridge/src/{runtime,vpn_backends,lib}.rs`. Выносим его
в новый крейт без UI и FFI:

- `crates/engine`: `Engine::{import, connect, disconnect, status, statuses,
  test_delay, exit_ip, route_check, diagnose}`.
- Платформенные адаптеры — трейты:
  - `Privileged` (хелпер по сокету | in-process исполнители);
  - `UserRuntime` (Xray-процесс `TunnelManager`, `SystemProxyManager`).
  Реализации — только macOS. Для Windows/Linux трейты остаются без
  реализации (коллега подключает демон и elevation).
- `crates/macos-bridge` становится тонкой C ABI-обёрткой над `Engine`:
  поведение и JSON-контракт Swift-клиента не меняются. Рефакторинг
  принимается только при зелёных `swift test` и `scripts/macos-dev.sh check`.
- `src-tauri` в этом этапе **не трогаем**.

Порядок внутри этапа (каждый шаг компилируется и проходит тесты):
1. Перенос чистых функций (`find`, `is_tun`, `resolver_bypass`,
   `request_tunnel`, статусы) в `engine`, bridge вызывает их.
2. Перенос `Session`/`with_session` и рекавери (`recover`).
3. Трейт `Privileged` + две реализации (`HelperSocket`, `InProcess`).
4. Тонкий bridge; удаление дублей.

## Этап 1: `crates/cli`, бинарник `netorch`

`clap`, `--json` у всех команд, коды выхода, completions. Данные в общем
каталоге приложения (как у GUI; переопределяется `NETORCH_MACOS_DATA_DIR`,
как у QA-режима).

```
netorch up   <vless://… | https://sub | wg.conf | .ovpn | имя>   [--tun | --socks N | --system-proxy]
             [--role secondary --networks CIDR…] [--direct geo:ru] [--proxy domain:x] [--block geo:ads]
netorch down [имя | --all]
netorch status | ls | logs <имя>
netorch add | rm | rename | edit
netorch sub refresh|endpoints|switch
netorch test [имя]            # задержки, exit-IP
netorch route check <host|ip>
netorch doctor
netorch backend install xray  # managed Xray, hash-pinned
netorch service status        # хелпер и режим привилегий
netorch completions zsh|bash|fish
```

Правила безопасности:
- секреты не аргументами: `-` читает stdin, `--password-stdin` для OpenVPN;
- вывод и `--json` проходят существующие редакторы секретов (`log_sanitize`,
  `redact_runtime_log`); UUID/ключи/URI не печатаются;
- запись конфигов только через `ConfigVault`, генерация Xray через
  `store_generated_xray`.

### Жизненный цикл

- Первичный релиз — foreground: `netorch up` держит процесс, Ctrl+C/SIGTERM
  откатывает (как `wg-quick`/sing-box). Нужен для пользовательского Xray и
  для режима 1 (исполнители в процессе).
- `--detach` (супервайзер с pidfile) — второй релиз.
- Туннели, живущие в хелпере (режим 2), переживают CLI.

## Этап 2: тесты и выпуск

- Юнит-тесты на фейковых платформах, TDD, RED/GREEN.
- Тест «CLI от root не запускает Xray от root»: фейковый запуск проверяет
  сброс uid/gid.
- `scripts/macos-dev.sh` получает подкоманду для CLI; `scripts/build-macos-native.sh`
  кладёт `netorch` в бандл и подписывает тем же `CODESIGN_IDENTITY`.
- `docs/platform-matrix.md`: строка про CLI; `CHANGELOG.md`; `AGENTS.md` —
  описание крейтов `engine`, `cli`.

## Передача коллеге (Windows/Linux)

Нужно реализовать `Privileged`/`UserRuntime` для своей платформы
(Linux: `DaemonClient` + polkit; Windows: elevation + in-process маршруты) и
перевести `src-tauri/src/commands/tunnels.rs` на `Engine`. Контракт `Engine`
и тесты на фейках — общие.

## Решено в ходе работы и что осталось

- Закреплённый OpenVPN берётся из бандла: `netorch` живёт только внутри
  `.app` (симлинк в PATH), копия хелпера знает бандл через `--bundle`.
- Порядок: сначала `sudo`-режим, затем хелпер как основной — оба сделаны.
- Не сделано: проверка подписи кода в политике пиров; `--detach`;
  самоповышение через `sudo`/`osascript`; перенос библиотеки профилей из
  `macos-bridge` в `engine`; Windows/Linux (адаптеры `Privileged`/`UserRuntime`
  — задача коллеги).
