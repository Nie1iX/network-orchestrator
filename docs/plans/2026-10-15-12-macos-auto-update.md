# macOS: автообновление приложения вне App Store (2026-10-15)

**Статус:** план, ничего не реализовано. Кнопка «Проверить обновления» в
Настройках (`NetworkViews.swift`) сейчас отключена с подсказкой «App updates
are not implemented for local native builds».

## Цель и рамки

- Пользователь видит, что вышла новая версия, читает заметки и ставит её из
  приложения, без ручной загрузки архива.
- Распространение идёт мимо App Store, без нотаризации: пользователи один раз
  увидят предупреждение Gatekeeper при первой установке. Это принято.
- Проверка обновлений — единственный сетевой запрос приложения «в домой»;
  она опциональна и отключаема в Настройках. Никаких идентификаторов, ключей и
  содержимого конфигураций в запросе нет (`AGENTS.md`, правила безопасности).
- Windows/Linux-клиенты не затрагиваются (у Tauri свой updater, отдельный план).

## Выбор механизма

**Sparkle 2** (SwiftPM-пакет `sparkle-project/Sparkle`): стандарт для macOS-
приложений вне App Store. Берёт на себя appcast, диалог, загрузку, проверку,
замену бандла и перезапуск. Альтернатива «свой запрос к GitHub API + открыть
страницу загрузки» проще, но не защищает скачанный файл и не ставит обновление;
оставляем её как запасной вариант, если Sparkle не уживётся с хелпером.

Подлинность обновления обеспечивает **EdDSA-подпись архива** (ключ Sparkle), а
не Apple Developer ID: публичный ключ лежит в `Info.plist`
(`SUPublicEDKey`), приватный хранится у мейнтейнера (Keychain) и никогда не
попадает в репозиторий и CI-логи.

## Хостинг

- Архивы `Network-Orchestrator-X.Y.Z.zip` (через `ditto -c -k --keepParent`)
  лежат в GitHub Releases тега `vX.Y.Z` (теги уже ведутся по
  `docs/versioning.md`).
- `appcast.xml` — статический файл (GitHub Pages или ассет последнего релиза),
  URL задаётся в `SUFeedURL`. Только HTTPS.
- В каждой записи: версия (`sparkle:version` = `CFBundleVersion`,
  `shortVersionString`), `sparkle:minimumSystemVersion` = 27.0, длина и
  `sparkle:edSignature` архива, ссылка на заметки (из `CHANGELOG.md`).

## Этапы

### Этап 1 — каркас Sparkle

1. `macos/Package.swift`: зависимость Sparkle (точная версия, не диапазон),
   линковка в `NetworkOrchestrator`.
2. `scripts/build-macos-native.sh`: класть `Sparkle.framework` в
   `Contents/Frameworks/`, подписывать вложенные компоненты (`Autoupdate`,
   `Updater.app`, XPC, затем framework) **до** подписи бандла, тем же
   `SIGN_ID`; без `--deep`. Хелпер подписывается как раньше.
3. `Info.plist` из скрипта сборки: `SUFeedURL`, `SUPublicEDKey`,
   `SUEnableAutomaticChecks = false` (включает пользователь),
   `SUScheduledCheckInterval` = сутки, `SUAllowsAutomaticUpdates = false`.
4. Тест: бандл собирается и подписывается; `codesign --verify --strict`
   проходит; приложение запускается без Sparkle-ошибок в консоли.

### Этап 2 — интеграция в UI

1. Тонкая обёртка `AppUpdater` над `SPUStandardUpdaterController` (одна точка
   входа, `@MainActor`), создаётся в `NetworkOrchestratorApp`.
2. Настройки → «Обновления приложения»: кнопка «Проверить обновления»
   (`checkForUpdates`), переключатель «Проверять автоматически», дата
   последней проверки. Снимается disabled-заглушка.
3. Пункт меню «Проверить обновления…» в меню приложения.
4. Новые строки — сначала в `locales/en.json`, затем `ru.json` и
   `npm run i18n:generate`.
5. Swift-тест на обёртку с поддельным драйвером; реальная сеть в тестах не
   используется.

### Этап 3 — выпуск

1. `scripts/release-macos.sh`: собрать бандл → zip → `sign_update` (приватный
   ключ из Keychain) → дописать `<item>` в `appcast.xml` → вывести команды
   `gh release create`. Публикацию делает человек, скрипт ничего не пушит.
2. Правило в `docs/versioning.md`: релиз macOS = тег `vX.Y.Z` + архив +
   запись в appcast. Заметки берутся из секции `CHANGELOG.md`.
3. Одноразовая генерация ключей (`generate_keys`), резервная копия приватного
   ключа вне репозитория. Потеря ключа = пользователи не смогут обновиться
   автоматически, придётся ставить вручную; ротация описывается отдельно.

### Этап 4 — привилегированный помощник после обновления

Это главная особенность нашего приложения. Замена бандла меняет хеш
`network-orchestrator-helper`, а launchd отказывается от старой регистрации
(`macos-build-and-sign`). Что нужно:

- Перед установкой обновления приложение отключает активные туннели штатным
  путём (rollback системного прокси, остановка Xray/OpenVPN/WireGuard) — в
  Sparkle это `updater(_:willInstallUpdate:)` / `updaterShouldRelaunchApplication`.
- После первого запуска новой версии срабатывает уже существующий баннер
  «helper outdated» и переустановка через `SMAppService`. В диалоге обновления
  и заметках к релизу явно сказать, что помощник придётся подтвердить заново
  в Настройки → Объекты входа.
- Политика пира в хелпере (путь процесса внутри бандла) не меняется: путь
  бандла остаётся тем же, меняется только содержимое.
- Проверить на живой установке: туннель выключается до замены, после
  перезапуска ни маршруты, ни DNS не остаются от старой версии
  (журнал владения хелпера чистится `recovery.cleanup`).

## Риски и открытые вопросы

- **Подпись.** Sparkle сверяет EdDSA-подпись; дополнительно сверяется Apple-
  подпись бандла, если она есть. При смене сертификата (Apple Development →
  Developer ID) нужно проверить цепочку обновления на реальном Mac. Ad-hoc
  сборки не регистрируют хелпер через `SMAppService`, поэтому для чужих
  машин нужен хотя бы платный Developer ID; без него хелпер-функции у
  пользователей работать не будут, и автообновление этого не исправляет.
- **Карантин.** Скачанный Sparkle архив не получает quarantine-атрибут, так что
  Gatekeeper спрашивает только при первой установке вручную.
- **Права на запись.** Если приложение лежит в `/Applications` и пользователь
  не админ, Sparkle запросит пароль через собственный установщик; это
  стандартное поведение, для нашего хелпера отдельного доступа не требуется.
- **Downgrade и канал.** Нужен ли бета-канал (`sparkle:channel`) — решить
  позже; сначала один стабильный.
- **Приватность.** Sparkle по умолчанию не шлёт профиль системы; оставить
  `SUEnableSystemProfiling` выключенным.

## Проверка перед закрытием плана

```bash
swift test --package-path macos --scratch-path target/macos-swift
cargo fmt --all -- --check && cargo check --workspace --all-targets
cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace
npm run build && npm run test && npm run test:i18n
```

Плюс ручная проверка: установить N, опубликовать N+1 в тестовом appcast
(локальный HTTPS-хост или файловая схема только для отладки), убедиться в
диалоге, замене, перезапуске и работе баннера помощника. Установленное в
`/Applications` рабочее приложение для этой проверки не использовать.
