# Predicted and Effective Route Map Implementation Plan

**Goal:** Visualize how active and proposed profiles compose into one Windows route map and explain the winning path for every prefix.

**Architecture:** Build a pure route-plan engine from static analyses and compare it with the effective Windows route table. Preserve longest-prefix match, then metric ordering, and highlight backend behavior that can override normal routing such as the WireGuard kill-switch.

**Tech Stack:** Rust route planner, Tauri commands, React/TypeScript

---

### Task 1: Add route-plan models

Represent owner, source, destination, interface, route metric, interface metric, effective metric, state, and predicted/effective provenance.

### Task 2: Build prefix hierarchy

Create a deterministic IPv4/IPv6 prefix tree. Nested prefixes are children, not conflicts. Exact duplicate prefixes form competing candidates ordered by effective metric.

### Task 3: Compute predicted winners

Combine active profiles, a draft candidate, static backend routes, app policy routes, and current OS routes. Mark unknown OpenVPN pushes and encrypted configs explicitly.

### Task 4: Compare effective state

After connect, join predicted entries to actual Windows routes and report missing, unexpected, changed-interface, and changed-metric outcomes.

### Task 5: Extend route lookup

Return both the actual winner and the predicted ownership explanation for a destination IP.

### Task 6: Build route-map UI

Add owner-colored expandable prefix trees, filters, exact-route competition, LPM explanation, and predicted/effective diff mode.

### Validation

Test `/8` + `/16` + `/24`, exact prefixes with metrics, IPv4/IPv6 separation, defaults, unknown routes, and WireGuard `/0` behavior.

```bash
cargo test -p net-manager-core route_plan
npm run build
```

## Implemented notes (stage 6)

- `AnalyzedRoute` gained `metric: Option<u32>`; profile policy routes carry `Some(route.metric)`, WireGuard/OpenVPN/Xray config-derived routes report `None` (no invented metrics).
- `route_plan` module: `build_route_map(profiles: &[(Profile, bool)], effective)`, `predicted_winner(destination, routes)`, `parent_prefix(index, routes)`.
- Predicted sort: IPv4 before IPv6, then network address, then ascending prefix (parent before child), then owner profile id — enables tree rendering via `parent_prefix` (nearest earlier broader route, same family).
- Winner policy: active routes only; longest prefix match, then lower known metric (`Some` beats `None`), then lexicographic owner profile id.
- Diff rules apply to active predicted routes only: `Missing` (no exact effective destination/prefix), `InterfaceMismatch` (exact routes exist, expected interface set, none match), `ExactCompetition` (2+ active predictions for the same exact prefix from different profiles, one diff per prefix). Unrelated baseline OS routes and nested-prefix overlap are not diffs.
- Analysis failures produce a warning containing profile name/id only — no config path/content.
- Tauri `get_route_map(include_inactive)`: loads profiles, takes one runtime lock to collect running flags, omits stopped profiles unless requested, lists routes, builds map.
- UI `RouteMap` on the Routes tab above lookup/table: "Include stopped profiles" checkbox, predicted tree rows (indentation via local parent calculation), differences, compact effective summary; refreshes on `route-changed`.
- Deferred (original tasks 3/5 remain follow-ups): draft-candidate merge, LPM explanation in route lookup, OpenVPN push-route marking, expandable UI.
