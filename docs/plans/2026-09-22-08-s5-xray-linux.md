# S5 — Xray на Linux

**Дата:** 2026-09-22 · **Основание:** [Ubuntu completion spec](2026-09-22-02-ubuntu-completion-spec.md) §3 D1–D3, D5–D6; §5.D; §6 UC09–12; §7 S5 и [backend facts](2026-09-22-05-backend-facts.md). **Статус:** VLESS/Hysteria2 SOCKS5/HTTP interop проверен в Docker; TUN/daemon install и desktop acceptance остаются.

## Результат и границы

На Ubuntu 26.04 пользователь импортирует VLESS/REALITY и `hysteria2://`/`hy2://`, подключается через локальные SOCKS5 и HTTP, управляет подпиской и её endpoint'ами, применяет domain/IP presets и включает Xray TUN через daemon. TUN получает адрес, routes, rules и per-link DNS; транспорт Xray не зацикливается; disconnect и recovery убирают ресурсы. Приёмка — UC09–12 в disposable Docker E2E и на чистой Ubuntu VM, плюс quality gate из `AGENTS.md`.

S5 не включает другие share-link схемы, Linux system proxy, auto-connect/tray (S6), упаковку `.deb` (S7), скрытую загрузку новых geo-файлов или автоматическое обновление Xray. Обычные tests не меняют сеть хоста.

## Проверенная отправная точка и решение о версии

- **inspected:** `crates/core/src/xray.rs` генерирует только VLESS `tcp/ws/grpc`, SOCKS inbound и TUN с ошибочными `interfaceName`/`ip`; `crates/core/src/vpn.rs::prepare_xray_config` передаёт полный TUN config в `xray run -test` и запускает Xray в локальном `TunnelManager`. На Linux runtime нужно перевести в daemon; Windows path не трогать.
- **inspected:** `src-tauri/src/commands/profiles.rs` принимает только `vless://`, хранит endpoint'ы в sidecar и переключает их по индексу. Нет refresh, latency, счётчика пропусков и лимита размера ответа. `SubscriptionMeta`/`SubscriptionEndpointInfo` в `crates/core/src/models.rs` и `src/types.ts` отражают эту схему.
- **inspected:** `crates/core/src/managed_xray.rs` сейчас pin **Windows v26.7.28**; `src-tauri/src/commands/system.rs` включает installer только на Windows. Спецификация и [факты](2026-09-22-05-backend-facts.md) проверяли Linux **v26.3.27**. Для S5 закрепить отдельные platform archive, SHA-256 и hashes `xray`/`geoip.dat`/`geosite.dat`; не менять Windows pin и не переносить поведение новых TUN версий на 26.3.27. Перед реализацией сохранить проверенный hash из официального release artifact, затем проверить `xray version` и JSON через этот exact binary.
- **upstream checked:** официальный [release v26.3.27](https://github.com/XTLS/Xray-core/releases/tag/v26.3.27) включает Hysteria2; tagged [TUN config](https://raw.githubusercontent.com/XTLS/Xray-core/v26.3.27/infra/conf/tun.go) и [Linux implementation](https://raw.githubusercontent.com/XTLS/Xray-core/v26.3.27/proxy/tun/tun_linux.go) — источник схемы для pin. Текущая [TUN документация](https://xtls.github.io/en/config/inbounds/tun.html) описывает дополнительные поля новых версий и сама [предупреждает о расхождении docs и установленной версии](https://xtls.github.io/en/config/). Поэтому для pinned 26.3.27 используем только `name`/`mtu`, а адреса и маршруты создаёт daemon.

## Инкременты RED → GREEN

1. **Share links и outbound config.** В `crates/core/src/xray.rs` сначала RED cases для VLESS `raw`/`xhttp`/`httpupgrade`, `alpn`, `spx`, REALITY, процента в URI и `hysteria2`/`hy2` (auth, SNI, `pinSHA256`, Salamander, port hopping); проверить generated JSON через pinned `xray run -test` без TUN. GREEN: один dispatch по схеме и минимальные serializers, без логирования URI. Hysteria JSON: `protocol:"hysteria"`, `settings.version:2`, `streamSettings.network:"hysteria"`, `security:"tls"`; `insecure=1`/`allowInsecure=1` и неподдерживаемый `obfs=gecko` отклонять с безопасной подсказкой. Остальные схемы только учитывать как skipped. → **verify:** `cargo test -p net-manager-core xray`; pinned Xray `-test`; реальный VLESS/REALITY и Hysteria2 interop в `e2e/linux/scenarios.sh`. Сверять с [VLESS share-link стандартом](https://github.com/XTLS/Xray-core/discussions/716), [Hysteria URI](https://v2.hysteria.network/docs/developers/URI-Scheme/), [Xray Hysteria outbound](https://xtls.github.io/en/config/outbounds/hysteria.html) и [transport compatibility](https://xtls.github.io/en/config/transport.html).
2. **Локальный SOCKS5 + HTTP и policies.** RED cases на loopback binding, разные свободные ports, SOCKS UDP, HTTP CONNECT и прежние пользовательские JSON. GREEN: добавить отдельный HTTP inbound для generated profiles в `crates/core/src/xray.rs`, доступный port в `crates/core/src/models.rs`/`src/types.ts`, форму и отображение в `src/components/ProfileFormModal.tsx`/`ProfileManager.tsx`; сохранить уже выбранный SOCKS port. В `apply_domain_policies` расширить rule model до IP (`geoip`) и block, presets private/LAN direct и `geosite:<cat>` direct/proxy/block, с явным порядком относительно пользовательских rules. Не трактовать `geoip:` как domain. → **verify:** core tests; `curl --socks5-hostname` и `curl --proxy http://` через оба inbound в E2E, включая правило direct/block. [Xray routing](https://xtls.github.io/en/config/routing.html), [HTTP inbound](https://xtls.github.io/en/config/inbounds/http.html).
3. **Подписки и latency.** RED cases: plain/base64 с VLESS, Hysteria2 и чужими схемами; bounded malformed body; refresh с перестановкой/удалением endpoint'ов сохраняет выбранный stable key, при его исчезновении выбирает явный fallback; ошибка fetch не портит старую ревизию. GREEN в `src-tauri/src/commands/profiles.rs`, `crates/core/src/config_vault.rs`, `crates/core/src/models.rs`, `src/types.ts`, `src/components/ProfileManager.tsx`: manual/interval refresh, `subscription-userinfo`, число skipped, атомарная смена sidecar+vault+profile и миграция старого `active_index`. Стабильный ключ — нормализованный URI без display fragment (секретный; не возвращать в UI/логи), для duplicates — детерминированный ordinal. TCP connect latency обозначить только как reachability; real delay мерить через временный SOCKS + `GET generate_204` с timeout, затем гарантированно остановить процесс. Не менять запущенный профиль до отдельного disconnect/reconnect. Auto-select лучшего endpoint'а — после ручного сценария. → **verify:** app command tests с fake HTTP и fake Xray; Docker E2E refresh, switch, real delay, сохраняемый selection и rollback.
4. **Linux managed Xray и geo assets.** RED cases на wrong archive/file hash, oversized ZIP, path traversal/symlink, неполный install, rollback и tampered geo. GREEN в `crates/core/src/managed_xray.rs`, `crates/core/src/daemon_protocol.rs`, `crates/daemon/src/server.rs`, `src-tauri/src/commands/system.rs`, `src-tauri/src/state.rs`: Linux x86_64 release pin, bounded allowlist extraction, atomic install и hash verification трёх обязательных файлов; в UI offer показывать именно Linux source. Для SOCKS app может использовать user-owned install. Для **TUN** daemon запускает только root-owned system binary с проверенной совместимой версией или root-owned verified managed copy: пользовательский `~/.local/bin/xray`, даже с совпавшим hash, от root не исполнять. Отдельный daemon install RPC принимает archive bytes, заново проверяет pin/hash и атомарно кладёт root-owned файлы в свой каталог; daemon не доверяет app-side проверке. `XRAY_LOCATION_ASSET` направить на verified geo assets. → **verify:** synthetic archive tests без сети; pinned binary + geo preset в Docker. [Xray routing geo syntax](https://xtls.github.io/en/config/routing.html), [Xray asset path](https://xtls.github.io/en/config/env.html); не включать [geodata auto-download](https://xtls.github.io/en/config/geodata.html).
5. **Daemon TUN transaction.** RED в `crates/core/src/xray.rs`, `crates/daemon/src/xray.rs` (новый), `crates/daemon/src/core.rs`/`server.rs`/`journal.rs`, `crates/core/src/daemon_protocol.rs` и `src-tauri/src/commands/tunnels.rs`: invalid/foreign executable, interface collision, failed spawn/address/rule/route/DNS, polkit denial, journal recovery и межпользовательский доступ — без leftovers. GREEN: `xray.connect`/`disconnect`/`status` по `SO_PEERCRED`, config bytes через socket без user path, redact Debug/errors; ограничить frame/config/rules. В daemon: `-test` **без TUN inbound**, запуск pinned Xray с явным уникальным `name` (≤15 bytes) и `mtu`, ожидание link, затем IP/MTU, отдельная table + `not fwmark`/`suppress_prefixlength 0`, per-link DNS через существующий S3 runtime. В `streamSettings.sockopt.mark` пометить все dialling outbounds, **включая `freedom`**, кроме `blackhole`. Записать владение процессом/link/address/rules/routes/DNS в journal, rollback в обратном порядке, PID/cgroup cleanup при restart; TUN Xray не получает user-writable binary. SOCKS остаётся без root; daemon TUN — отдельный Linux path. → **verify:** fake executor RED/GREEN; `e2e/linux/scenarios.sh` проверяет трафик, отсутствие петли, DNS, disconnect и `kill -9` daemon; запуск только через `e2e/linux/run.sh`. Для pinned 26.3.27 `-test` с TUN создаёт link и может дать `EBUSY`, см. [backend facts](2026-09-22-05-backend-facts.md) §1–2.

## Риски и условия выхода

- S3 full-tunnel tables/DNS и S4 process supervision могут ещё не быть в текущем daemon: S5 должен переиспользовать их после фактического merge, не копировать несовместимый runtime. Сейчас `server.rs` объявляет только route methods в `hello.capabilities`; будущие `wireguard.*` constants сами по себе не означают готовую реализацию. **inspected.**
- `SO_MARK` для root Xray требует достаточной capability в systemd unit; проверить именно с итоговым hardening, а также работу Hysteria UDP и `freedom` при full tunnel. Нельзя считать TCP latency доказательством работающего proxy. **inferred; verify in E2E.**
- DNS и IPv6 должны честно показывать охват: `0.0.0.0/0` не покрывает IPv6; если `::/0` не настроен, UI не обещает весь трафик. При недоступном systemd-resolved — явный diagnostic. **inferred from S3 contract.**
- Секреты в URI, `X-HWID`, HTTP headers, JSON config и Xray stderr не включать в ошибку, sidecar preview или daemon journal; тестировать redaction на malformed subscription и failed connect. **required by spec.**

**Выход S5:** RED/GREEN записаны для каждого инкремента; пройдены `cargo fmt --all -- --check`, `cargo check --workspace --all-targets`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `npm run build` и `e2e/linux/run.sh`; UC09–12 отдельно подтверждены на Ubuntu VM. Если Docker/VM недоступны, сообщить, что interop/TUN приёмка не проверена.
