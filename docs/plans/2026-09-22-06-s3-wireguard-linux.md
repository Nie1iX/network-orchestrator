# S3 — WireGuard на Linux, full tunnel и per-link DNS

**Дата:** 2026-09-22 · **Основание:** [Ubuntu completion spec](2026-09-22-02-ubuntu-completion-spec.md) §3 D1–D3, D5–D6; §5.B; §6 UC03–05; §7 S3. **Статус:** реализовано и проверено в Docker (38 базовых + 23 WG checks); приёмка через UI на чистой Ubuntu остаётся.

## Цель и границы

На Ubuntu пользователь импортирует обычный WireGuard `.conf`, подключает split или full tunnel и видит handshake. Daemon от root владеет созданным link, его адресами, routes, rules, mark и DNS. `disconnect`, ошибка connect, SIGTERM и restart daemon'а убирают только его ресурсы. Full tunnel не захватывает собственный UDP-транспорт WireGuard, а DNS из `DNS=` применяется через systemd-resolved.

S3 не включает OpenVPN/Xray TUN, always-on, reconnect после смены сети, kill switch и восстановление туннеля после краша daemon'а: restart пока чистит leftovers; повторное поднятие always-on — S6. Не запускать `wg-quick` и пользовательские hook-команды от root. Windows-путь `TunnelManager` оставляем как есть.

**Приёмка S3:** UC03, UC04 и UC05 проходят на чистой Ubuntu 26.04 VM и в двухконтейнерном E2E ниже; оба семейства IP проверены там, где они объявлены в `AllowedIPs`. Все пять команд quality gate из `AGENTS.md` проходят на Linux. Обычные unit tests не меняют сеть хоста.

## Исходное состояние на момент планирования

- **inspected:** `crates/core/src/daemon_protocol.rs` знает только `routes.*`, `link.set_state`, `owned.list`, `recovery.cleanup`, `subscribe`; `OwnedResource` содержит лишь `Route`. Для WG нужен один daemon RPC на весь connect, иначе нельзя сделать атомарный rollback.
- **inspected:** `crates/daemon/src/core.rs::DaemonCore` журналирует routes до netlink, но `teardown_entry` умеет удалять только routes. `crates/daemon/src/journal.rs::JournalStore` сохраняет 0600 через temp+fsync+rename и блокирует старт при повреждённом или неизвестном журнале.
- **inspected:** `crates/daemon/src/netlink.rs::NetlinkExecutor` имеет route table и link up/down, но не умеет создать/удалить WG link, назначить address/MTU или добавить `ip rule`. `route_request` ставит собственный `RTPROT` 79 и `NLM_F_EXCL`.
- **inspected:** `src-tauri/src/commands/tunnels.rs::connect_profile` сейчас запускает локальный `TunnelManager`, затем отдельно ставит routes через `runtime.policies`; `disconnect_profile` снимает их в обратном порядке. `get_tunnel_statuses` спрашивает только локальный `TunnelManager`. `src-tauri/src/state.rs::RuntimeState` пока держит локальные tunnels. Текущий Linux WG идёт через `crates/core/src/vpn.rs::resolve_wireguard_executable`, который ищет `wireguard.exe`.
- **inspected:** `crates/core/src/analysis.rs::analyze_wireguard` извлекает `AllowedIPs` и endpoint для preview, но принимает неполные configs с warnings; этот tolerant parser нельзя использовать как root-side validation. `crates/core/src/vpn.rs::wireguard_health_from_dump` уже умеет получать handshake/bytecount без выдачи ключей.
- **inspected:** `e2e/linux/run.sh` поднимает один client-контейнер. `e2e/linux/Dockerfile` уже ставит `wireguard-tools` и `systemd-resolved`; `e2e/linux/scenarios.sh` проверяет только S1 routes и recovery.
- **confirmed by upstream documentation:** `wg setconf` принимает только формат `wg(8)`, тогда как `Address`, `DNS`, `MTU`, `Table` и hooks — расширения `wg-quick`; `wg-quick strip` описан как способ удалить их. Используем собственный строго ограниченный parser и передаём в `wg setconf` только WG-поля. [WireGuard wg-quick manual](https://git.zx2c4.com/wireguard-tools/about/src/man/wg-quick.8), [wg manual](https://git.zx2c4.com/wireguard-tools/about/src/man/wg.8).

## Контракт и инварианты

1. Новый `wireguard.connect` принимает `profileId`, байты конфигурации и явные `profile.routes` (без пути к пользовательскому файлу). UI читает конфиг через существующий vault; daemon не принимает произвольный path и не читает home из-под root. `wireguard.disconnect` и `wireguard.status` принимают только `profileId`. Owner внутри daemon — `(SO_PEERCRED uid, "wg:" + profileId)`; по данным клиента uid не выбирается. `hello.capabilities` объявляет методы. Ошибки и события не содержат config, ключей, endpoint с credentials или dump целиком. Лимит размера остаётся `MAX_FRAME_BYTES`; отдельно ограничить число peers/addresses/routes и размер config.
2. В `crates/core/src/daemon_protocol.rs` добавить typed params/results/status и версии `OwnedResource` для `WireGuardLink`, `Address`, `Rule`, `Route`, `Dns` (хранить только метаданные, необходимые для cleanup: имя/index link, family, exact priority, mark/table, адрес, route, DNS ownership marker). **Не сохранять** приватный ключ или исходный `.conf` в `/var/lib/.../state.json`. Изменение persisted schema требует явной миграции `JOURNAL_VERSION` и теста чтения S1-журнала; старые route-записи должны оставаться убираемыми.
3. Валидация daemon до polkit и первой мутации: ровно поддержанные секции/ключи `[Interface]` и `[Peer]`; `PrivateKey`, `PublicKey`, `PresharedKey`, `Endpoint`, `AllowedIPs`, `PersistentKeepalive`, `ListenPort` проверяются по типу и пределам; `Address`, `MTU`, `DNS`, `Table` разбираются приложением. `PreUp`, `PostUp`, `PreDown`, `PostDown`, `SaveConfig` игнорируются с безопасным предупреждением без значения; неизвестные поля, `FwMark` пользователя и numeric `Table` отклоняются с именем поля. `Table=off` запрещает routes, выводимые из `AllowedIPs`, но явные `profile.routes` остаются применимыми; `Table=auto`/отсутствует включает вывод. В многопировой конфигурации policy destination должен быть покрыт `AllowedIPs` конкретного peer; неоднозначное расширение запрещено. Для одного peer можно сохранить прежнюю семантику `vpn.rs::expand_allowedips`: расширить `AllowedIPs` только явно указанными policy routes, но не DNS или endpoint незаметно.
4. Имя создаваемого link — детерминированное, daemon-generated, не длиннее 15 байт, например `wg-` + короткий hash `(uid, profileId)`. До записи/создания проверить отсутствие чужого link; `EEXIST` даёт `conflict`, чужой link нельзя принимать во владение. `wg` binary — только фиксированный root-owned путь, без пользовательских executable settings для daemon. Файл для `wg setconf` создаётся под `/run/network-orchestrator/<uid>/` с mode 0600, закрытым dir и без symlink-follow, удаляется после `setconf` и при rollback. Не писать его в journal, stdout/stderr с ключами не логировать.
5. **Split:** если `profile.routes` непустой, ставить только их; иначе `AllowedIPs` (кроме `Table=off`). `Address` назначить на WG link; connected routes ядра учитывать при дедупликации, чужие routes не заменять. Split routes ставить в `main` через существующий собственный RTPROT 79. Различать политику по v4/v6. DNS server для split должен быть достижим через выбранный WG peer/маршрут, иначе connect сообщает ошибку до применения DNS — не обещать per-link DNS через физический uplink.
6. **Full:** наличие `0.0.0.0/0` и/или `::/0` в *эффективных* routes переключает соответствующее семейство на отдельную daemon-allocated table `T` и mark `M` (допустимо `M=T`, если нет коллизии). До мутаций проверять занятость table/mark и двух rule priorities в обоих семействах, включая чужие rules и journal; нет безопасного слота → `conflict`. Только один активный full-tunnel owner глобально, в том числе между uid; второй отклонять до создания link. `wg set <if> fwmark M` маркирует transport UDP. Для каждого full family: route `/0 dev wg-* table T`; явные более узкие WG routes — в `main` при необходимости. Два rules с явными сохранёнными priorities должны давать порядок `lookup main suppress_prefixlength 0` → `not fwmark M lookup T` → штатный `main` default. Так более узкие LAN routes остаются в `main`, немаркированный default идёт в WG, а помеченный WG UDP до endpoint доходит через старый default. Проверять `ip route get <endpoint-ip> mark M` и `ip route get <probe-ip>`; не полагаться только на наличие rules. [Реализация wg-quick](https://git.zx2c4.com/wireguard-tools/tree/src/wg-quick/linux.bash), [ip-rule(8)](https://man7.org/linux/man-pages/man8/ip-rule.8.html).
7. Endpoint с hostname разрешается **до** установки full rules; `wg setconf` получает уже разрешённый IP или эквивалентно выполняется до переключения routing. Нет отдельного постоянного `/32` до endpoint: достижимость обеспечивает `fwmark` и fallback в `main`. При изменении сети daemon в S3 сохраняет честный статус `failed`/`reconnecting`, если handshake прекращается; автоматический re-resolve/reconnect — S6. Full v4 без `::/0` остаётся v4-only: UI/diagnostics явно показывают покрытые семейства и предупреждают о прямом IPv6; не показывать «весь трафик защищён». Kill switch не вводится — при разрыве WG трафик может перестать проходить или идти по иной существующей политике.
8. **DNS:** только при наличии `DNS=` и активном systemd-resolved. После появления link применить `resolvectl dns <if> <IP...>` и `resolvectl domain <if> ~.` для full; для split — только явно заданные домены как route-only `~domain` (не делать глобальный DNS из split-профиля без доменов). `resolvectl default-route <if> no` для split, `yes` для full, если эта функция поддерживается целевой версией; подтвердить в E2E. Команда вызывается daemon'ом через фиксированный root-owned binary и argv, без shell; диагностика отличает `resolved unavailable` от ошибки настройки. При отсутствии resolved оставить туннель поднятым и вернуть явный `dnsNotApplied` warning по spec, не заявляя отсутствие DNS leak. Настройки применять заново при restart resolved, пока WG link активен. `revert` только на созданном daemon WG link, до удаления link; никогда не вызывать его на физическом/чужом интерфейсе. Upstream рекомендует per-link `SetLinkDNS`, `SetLinkDomains`, `SetLinkDefaultRoute` и `RevertLink` после появления интерфейса; CLI здесь следует тому же контракту. [systemd-resolved network-manager API](https://wiki.freedesktop.org/www/Software/systemd/writing-network-configuration-managers/), [resolve1 D-Bus API](https://www.freedesktop.org/software/systemd/man/247/org.freedesktop.resolve1.html).
9. **Журнал/transaction:** до *каждого* side effect записать `applying` и намерение владения конкретным ресурсом, затем выполнить действие. Порядок: reserve owner/table/mark/priorities → temp config → create link → `wg setconf`/`fwmark` → addresses/MTU → link up → routes → rules → DNS → `applied`; rollback/teardown строго обратно: DNS → rules → routes → addresses → link → temp config. Failure оставляет только фактически неубранные ресурсы как `stale`; `NotFound` при cleanup считается успехом. Delete сверяет точные атрибуты owner, link/index, rule priority/selector/table и RTPROT перед удалением; не удалять совпавший чужой ресурс после reuse. Если journal повреждён/неизвестной версии, daemon **не должен молча стартовать с пустым ownership**: остановить мутации с diagnostics до ручного восстановления или безопасного reconcile. При restart resolved DNS надо восстановить из journal, без секретов; после restart daemon cleanup, как в S1.
10. RPC делает preflight/authorization один раз (`com.netmanager.app.connect-profile`), потом вызывает одну транзакцию `DaemonCore::connect_wireguard`. `routes.apply/remove` остаются только для static-route owners; они не могут частично удалить WG owner. `owned.list`/`wireguard.status`/events scoped по uid. UI-аналитику конфликтов оставить preview, daemon проверяет конфликты заново как authority. Статус берётся через `wg show <if> dump` или netlink для собственного link; parser из `vpn.rs` можно использовать, но raw dump нельзя отдавать клиенту. `Running` означает link/rules установлены, а handshake timestamp и traffic counters показываются отдельно; отсутствие handshake сразу после connect не равно падению.

## Двухконтейнерный E2E: что доказывать

`e2e/linux/run.sh` создаёт отдельную Docker network и два disposable контейнера: `client` (systemd, polkit, resolved, daemon) и `server` (kernel WireGuard peer, Python HTTP + DNS responders с счётчиками). Оба имеют собственные network namespaces; сценарий запускается только через `run.sh`, **никогда** непосредственно на host. Server нужен `CAP_NET_ADMIN`; client сохраняет текущие `NET_ADMIN`, `SYS_ADMIN`, `/dev/net/tun` и AppArmor opt-out для systemd. Тестовые ключи генерировать внутри контейнеров, не печатать их. При любой ошибке `trap` удаляет оба контейнера и сеть; `--keep` только для debugging. Перед WG-сценариями прогонять существующие S1 checks.

Для проверки петли нужен endpoint, достижимый **через underlay default**, а не через Docker connected route: назначить server дополнительный тестовый IP (например, `198.18.0.1/32`), а client default route временно направить через server Docker-IP внутри его namespace. WG `Endpoint` указывает `198.18.0.1:51820`. Тогда после установки full `ip route get 198.18.0.1` без mark выбирает WG table, а `ip route get 198.18.0.1 mark M` — underlay link. Реальный handshake и повторный обмен данными после переключения доказывают, что transport не зациклился. Server публикует отдельный адрес/HTTP service за WG, который client достигает через туннель; счётчик на server подтверждает путь. Проверить v4 и, если включён `::/0`, аналогично v6; сценарии должны различать семейства.

1. **Split:** `AllowedIPs=10.77.0.0/24`, `Address=10.77.0.2/32`. `wg show` сообщает handshake, HTTP на WG-адресе доступен; другой тестовый адрес выбирает underlay. Link, route proto 79 и journal появляются после connect и исчезают после disconnect. `profile.routes` как подмножество AllowedIPs ставит только эти routes (UC05).
2. **Full:** конфиг с `0.0.0.0/0` (и отдельный dual-stack fixture с `::/0`), `DNS=10.77.0.1`. Проверить `T`, `M`, точные priorities, `wg show fwmark`, оба `ip route get`, HTTP payload через WG, живой handshake после нескольких пакетов. Убедиться, что физический connected LAN route остаётся достижим.
3. **DNS:** DNS responder на WG-адресе возвращает уникальное имя; «leak trap» на underlay IP считает запросы. `resolvectl query` при full `~.` обращается к tunnel DNS и не увеличивает underlay counter; split с `~corp.test` направляет `*.corp.test` в туннель, другое имя — по underlay. После disconnect per-link DNS исчезает; после restart resolved при активном WG daemon применяет settings повторно. Отдельный прогон с остановленным resolved проверяет warning и отсутствие скрытой модификации `/etc/resolv.conf`.
4. **Ошибки/recovery:** неверный ключ/хук и отказ polkit не создают ресурсов; искусственный отказ DNS после успешных link/routes/rules откатывает их; конфликт чужого link/rule/table оставляет чужой ресурс без изменений. `kill -9` daemon → systemd restart → journal cleanup без leftover; SIGTERM делает teardown. `owned.list` и `wireguard.status` не показывают чужой uid и не выдают ключей.

После E2E на чистой Ubuntu 26.04 VM пройти UC03–05 через UI и проверить предупреждение про v4-only full/отсутствие resolved. Docker доказывает network mechanics, но не заменяет desktop/polkit agent acceptance.

## Критические риски перед стартом

- **Journal corruption:** `JournalStore::load` уже блокирует старт с повреждённым или неизвестным journal; шаг 1 должен сохранить это поведение при миграции формата, чтобы не получить orphaned link/rules/DNS.
- **Protocol frame/secret size:** `MAX_FRAME_BYTES=1 MiB`; inline WG config и лимиты должны быть зафиксированы до UI integration. Не передавать путь, не логировать raw request.
- **IPv6 и DNS semantics:** `0.0.0.0/0` не закрывает IPv6, а `~.` относится только к клиентам systemd-resolved. В UI нельзя обещать полный охват, если `::/0` нет или приложения обходят resolved. Это не блокирует S3, но обязательное явное ограничение.
- **Внешняя среда:** текущий `run.sh` одноконтейнерный, и сама S2 E2E может ещё меняться параллельно. Расширять его минимально, не переписывая проверки S1. Запуск контейнерного стенда требует работающего Docker и указанных capabilities; если они недоступны, итог S3 нельзя объявить E2E-проверенным.
